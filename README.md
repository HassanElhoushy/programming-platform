# منصة البرمجة

منصة تعليمية لمادة **البرمجة والذكاء الاصطناعي** — الصف الثاني الثانوي، نظام البكالوريا المصرية.

عربية بالكامل، اتجاهها من اليمين لليسار، وضع فاتح فقط. مستخدمان لا ثالث لهما: **مدرّس واحد** و**طلاب**.

**الستاك:** Next.js 16 (App Router) · TypeScript · Tailwind CSS v4 · Supabase · Vercel
**التكلفة:** صفر. كل شيء داخل الباقات المجانية.

## ١. التشغيل خطوة بخطوة

### أ. مشروع Supabase

المشروع منشأ بالفعل باسم `programming-platform` على Frankfurt. لو احتجت إنشاء واحد جديد يوماً ما: [supabase.com](https://supabase.com) ← New project ← اختر Region قريبة من مصر (`eu-central-1` أفضل خيار).

في **Authentication → Providers → Email** تأكد أن **Confirm email مقفول**. الطلاب لا يفتحون بريدهم، وتفعيله يعني خسارتهم عند التسجيل.

### ب. تنفيذ ملفات SQL

افتح **SQL Editor** في لوحة Supabase، ونفّذ ملفات مجلد `supabase/sql` **بالترتيب**، ملفاً ملفاً:

| الملف | ماذا يفعل |
|---|---|
| `01_schema.sql` | الأنواع والجداول والفهارس، وtrigger إنشاء ملف المستخدم عند التسجيل |
| `02_functions.sql` | دوال الصلاحيات التي تعتمد عليها سياسات RLS، ودالة تطبيع النص العربي |
| `03_rls.sql` | تفعيل RLS على كل جدول وكتابة السياسات |
| `04_rpc.sql` | بدء الامتحان، التصحيح الآلي، المراجعة، تصحيح المقالي |
| `05_storage.sql` | ضبط الـ buckets وإزالة أي سياسة وصول مباشر عليها |

الملفات قابلة لإعادة التشغيل، فلو غيّرت شيئاً وأعدت التنفيذ لن يحدث ضرر.

> `06_make_admin.sql` و`07_security_check.sql` و`08_smoke_test.sql` لها وقت آخر — انظر القسمين ٢ و٧.

بعد أن يصير لديك حساب مدرّس وحساب طالب مفعّل، شغّل `08_smoke_test.sql` مرة واحدة. يبني امتحاناً فيه الأنواع الخمسة، ويحلّه بشخصية طالب حقيقي، ثم يتحقق أن كل درجة خرجت كما هو متوقع — بما في ذلك أن «الذكاء الإصطناعى» تُقبل مقابل «الذكاء الاصطناعي»، وأن الإجابات الصحيحة محجوبة قبل أن تفتحها. ينتهي بـ `rollback` فلا يترك أثراً.

### ج. المتغيرات البيئية

انسخ `.env.example` إلى `.env.local` واملأه:

```
NEXT_PUBLIC_SUPABASE_URL=https://cpwhdvcfwngtlxzbgcmp.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
SUPABASE_SECRET_KEY=sb_secret_...
```

المفتاحان الأولان من **Project Settings → API Keys → Publishable key**، والثالث من **Secret keys** في نفس الصفحة.

المتغير الأول والثاني يظهران في المتصفح — هذا طبيعي ومقصود، والحماية كلها في سياسات RLS. أما `SUPABASE_SECRET_KEY` فيتخطّى كل سياسات الحماية، ولا يُوضع أبداً في متغير يبدأ بـ `NEXT_PUBLIC_`.

### د. التشغيل محلياً

```bash
npm install
npm run dev
```

افتح <http://localhost:3000>.

## ٢. كيف تصير حساب المدرّس

هذه أول خطوة بعد أول تشغيل، ولا يعمل شيء قبلها.

1. افتح `/signup` وسجّل حساباً ببريدك `hassanelhushy@gmail.com` واسمك ورقم موبايلك.
2. ستصل إلى صفحة "حسابك بانتظار الموافقة" — هذا متوقع، فكل حساب جديد يبدأ طالباً.
3. ارجع إلى SQL Editor ونفّذ `supabase/sql/06_make_admin.sql`. سيرفع حسابك إلى `admin`.
4. حدّث الصفحة، وستجد نفسك في لوحة المدرّس.

لو أردت لاحقاً تعيين بريد آخر، غيّر قيمة `v_email` في أول الملف ثم شغّله.

## ٣. النشر على Vercel

1. ادفع المشروع إلى GitHub (الريبو: `HassanElhoushy/programming-platform`).
2. [vercel.com/new](https://vercel.com/new) ← **Import Git Repository** ← اختر الريبو.
3. Framework سيُكتشف تلقائياً كـ Next.js. لا تغيّر شيئاً في إعدادات البناء.
4. في **Environment Variables** أضف الثلاثة:

   | الاسم | القيمة |
   |---|---|
   | `NEXT_PUBLIC_SUPABASE_URL` | رابط مشروعك |
   | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_...` |
   | `SUPABASE_SECRET_KEY` | `sb_secret_...` |

   ضعها في البيئات الثلاث (Production و Preview و Development).
5. **Deploy**.

بعد أول نشر، أي `git push` على الفرع الرئيسي ينشر تلقائياً.

### الجلسات الطويلة

المنصة مضبوطة ليبقى الطالب مسجّلاً لشهور: `persistSession` و`autoRefreshToken` مفعّلان، وملف `src/proxy.ts` ينادي `supabase.auth.getUser()` على كل طلب **قبل** إرجاع الاستجابة، فيتجدد التوكن ويُكتب على الكوكيز.

لتكتمل الصورة، افتح **Authentication → Sessions** في Supabase وتأكد أن:

- **Inactivity timeout** فارغ أو مطفأ (وإلا خرج الطالب بعد فترة سكون).
- **Time-box user sessions** فارغ أو مطفأ (وإلا خرج الطالب بعد مدة ثابتة مهما كان نشطاً).

> ملاحظة لمن يقرأ الكود: في Next.js 16 صار اسم ملف الـ middleware هو `proxy.ts`. الوظيفة نفسها، والاسم القديم مهجور.

## ٤. تفعيل الـ cron الذي يمنع توقّف المشروع

مشروع Supabase المجاني يتوقف تلقائياً إذا لم يحدث عليه نشاط لمدة **7 أيام**. ملف `.github/workflows/supabase-keepalive.yml` يرسل طلب قراءة بسيطاً كل يومين على جدول `heartbeat` الصغير.

لتفعيله:

1. من صفحة الريبو على GitHub: **Settings → Secrets and variables → Actions → New repository secret**.
2. أضف سرّين:
   - `SUPABASE_URL` = رابط مشروعك
   - `SUPABASE_PUBLISHABLE_KEY` = `sb_publishable_...`
3. من تبويب **Actions** اختر **Supabase keep-alive** ثم **Run workflow** لتجربته يدوياً مرة واحدة والتأكد أنه يعود بـ `HTTP 200`.

بعدها يعمل وحده كل يومين.

> **انتبه:** GitHub يوقف الـ workflows المجدولة تلقائياً إذا مرّ على الريبو **60 يوماً** بلا أي نشاط، ويرسل لك بريداً قبلها. لو وصلك ذلك البريد، ادخل تبويب Actions واضغط **Enable workflow**.

## ٥. كيف تستخدم المنصة يومياً

### إضافة محتوى

**المحتوى** ← **فصل جديد** ← داخل الفصل **درس جديد** ← افتح الدرس وارفع ملفات الـ PDF وأنشئ الامتحانات.

الترقيم الذي تكتبه هو ما يظهر للطالب بصيغة «الفصل الأول · الدرس الثاني». الحد الأقصى لملف الـ PDF هو 20 ميجابايت.

الحذف في هذه المنصة **أرشفة**: العنصر يختفي من حسابات الطلاب فوراً، لكن الدرجات والتسليمات المرتبطة به تبقى محفوظة.

### الموافقة على الطلاب وفتح المحتوى

الطالب يسجّل بنفسه، ويظهر في **الطلاب** بحالة «بانتظار الموافقة». الطالب في هذه الحالة **لا يرى شيئاً إطلاقاً**، ولا حتى عناوين الدروس.

افتح صفحة الطالب، ثم:

- **فعّل الحساب** ليتمكن من الدخول.
- افتح له محتوىً، بإحدى طريقتين:
  - **افتح كل الصلاحيات** — يرى كل شيء، وأي درس أو امتحان تضيفه لاحقاً يظهر له تلقائياً بلا خطوة إضافية.
  - **افتح الدرس كله**، أو علّم على ملف بعينه وامتحان بعينه.

السحب فوري: بمجرد إلغاء التعليم يختفي العنصر من حساب الطالب.

### إنشاء امتحان

من صفحة الدرس ← **امتحان جديد** ← عنوان ومستوى ومدة (اتركها فارغة إن أردته بلا وقت).

بعدها تنتقل إلى صفحة الامتحان، فاستورد الأسئلة من ملف JSON (القسم التالي)، ثم **افتح الامتحان**.

عدد الأسئلة يُحسب من الأسئلة المستوردة فعلاً، فلا يوجد حقل تكتبه بيدك ويتعارض مع الواقع.

### أثناء الامتحان وبعده

- إجابات الطالب تُحفظ لحظياً. لو انقطع النت أو أُغلقت الصفحة يعود ويكمل من مكانه.
- **انتهاء الوقت لا يغلق الامتحان ولا يسلّمه.** الطالب يكمل، والنظام يسجّل الوقت الفعلي ويضع علامة «تجاوز الوقت» تراها أنت.
- إغلاق الامتحان يمنع البدايات الجديدة فقط. من بدأ يكمل ويسلّم.
- بعد التسليم تُصحح الأسئلة الموضوعية آلياً في نفس اللحظة.

### التصحيح

**تصحيح الامتحانات** يعرض كل تسليم فيه سؤال مقالي غير مصحح. تفتح التسليم، فترى نص السؤال وإجابة الطالب — النص المكتوب والصورة المرفوعة معاً — وتدخل درجة وملاحظات لكل سؤال، ثم **إرسال التصحيح**.

يمكنك تعديل الدرجة أو الملاحظات في أي وقت لاحق، والتعديل يصل للطالب فوراً.

### إظهار الإجابات النموذجية

**مقفول افتراضياً في كل امتحان جديد.** ما دام مقفولاً، يرى الطالب درجته الكلية فقط، ولا يرى الإجابة الصحيحة ولا حتى أي سؤال أصاب فيه وأيّه أخطأ.

افتحه من صفحة الامتحان **بعد أن يخلص كل الطلبة**، وإلا سرّبها أول من يحل لزملائه.

### إعادة المحاولة

الطالب لا يستطيع حل الامتحان مرتين. لو حدث عطل حقيقي (انقطاع نت طويل، جهاز فصل) افتح صفحة الطالب ← الامتحان ← **اسمح بإعادة المحاولة**. المحاولة القديمة تُلغى ويبقى سجلها محفوظاً.

## ٦. صيغة ملف الأسئلة

الملف النموذجي الكامل في `public/sample-questions.json`، ويمكنك تنزيله من داخل صفحة الامتحان أيضاً.

```json
{
  "questions": [
    {
      "type": "mcq_single",
      "body": "أي من التالي يُعد لغة برمجة عالية المستوى؟",
      "points": 2,
      "options": ["لغة الآلة", "لغة التجميع Assembly", "بايثون Python", "الشفرة الثنائية"],
      "correct": 3
    },
    {
      "type": "mcq_multi",
      "body": "اختر كل ما ينطبق على أنواع البيانات في بايثون:",
      "points": 3,
      "options": ["int", "string", "printer", "float", "monitor"],
      "correct": [1, 2, 4]
    },
    {
      "type": "true_false",
      "body": "الذكاء الاصطناعي فرع من فروع علوم الحاسب.",
      "points": 1,
      "correct": true
    },
    {
      "type": "fill_blank",
      "body": "الحلقة [1] تُستخدم لتكرار عدد معروف من المرات، بينما الحلقة [2] تُستخدم عندما يكون عدد التكرارات غير معروف مسبقاً.",
      "points": 2,
      "blanks": [["for", "الحلقة for"], ["while", "الحلقة while"]]
    },
    {
      "type": "essay",
      "body": "اشرح الفرق بين المتغير والثابت، مع ذكر مثال لكل منهما.",
      "points": 5
    }
  ]
}
```

### القواعد

| الحقل | الشرح |
|---|---|
| `points` | اختياري، وقيمته الافتراضية `1` |
| `correct` في `mcq_single` | رقم الخيار الصحيح. **الترقيم يبدأ من 1 لا من صفر** |
| `correct` في `mcq_multi` | قائمة أرقام كل الخيارات الصحيحة |
| `blanks` في `fill_blank` | اكتب `[1]` و`[2]` داخل نص السؤال في مواضع الفراغات، ولكل فراغ قائمة بالإجابات المقبولة |
| `essay` | بلا مفتاح — تصححه بنفسك |

### كيف يُصحَّح كل نوع

- **اختيار واحد وصح/خطأ:** كامل أو صفر.
- **اختر كل ما ينطبق:** كامل أو صفر — لا بد أن يختار المجموعة بالضبط، بلا زيادة ولا نقصان.
- **إكمال الفراغات:** الدرجة تُوزَّع بالتساوي على الفراغات. من أصاب ثلاثة من أربعة أخذ ثلاثة أرباع الدرجة.
  والمقارنة تتجاهل التشكيل والتطويل، وتوحّد `أ إ آ ٱ` مع `ا`، و`ة` مع `ه`، و`ى` مع `ي`، و`ؤ ئ` مع `و ي`، وتحوّل الأرقام العربية إلى لاتينية، وتضغط المسافات الزائدة. بغير هذا كان «الذكاء الإصطناعى» سيُحسب خطأً أمام «الذكاء الاصطناعي».

### الاستيراد

- **استيراد ملف كامل** يستبدل كل أسئلة الامتحان. ويُرفض إن كان أحد الطلاب قد بدأ الامتحان بالفعل، لأن تغيير الأسئلة تحت محاولة جارية يفسد إجاباتها ودرجاتها.
- **إضافة سؤال واحد** تُلحق سؤالاً بالموجود، للحالات الفردية.
- أي خطأ في الملف يُعرض مرقّماً بالسؤال قبل حفظ أي شيء.

> الخيارات تظهر للطالب بترتيبها في الملف. نوّع موضع الإجابة الصحيحة بين الأسئلة حتى لا يخمّنها الطلبة من النمط.

## ٧. كيف مُنع الطالب من رؤية الإجابات، وكيف تختبر ذلك بنفسك

المفتاح العام يظهر في المتصفح بطبيعته. فالسؤال الحقيقي ليس «هل نخفي شيئاً في الواجهة» بل «ماذا يحدث لو فتح الطالب DevTools وكتب استعلاماً بيده». الجواب في أربع طبقات:

### ١. الإجابة الصحيحة ليست في جدول الأسئلة أصلاً

جدول `question_options` **لا يحتوي على عمود `is_correct`**. لا يوجد عمود منسيّ يمكن أن يُسرَّب سهواً. الصحة كلها في جدول منفصل اسمه `question_keys`، وسياسته الوحيدة:

```sql
create policy question_keys_admin_only on public.question_keys
  for all to authenticated
  using ( public.is_admin() )
  with check ( public.is_admin() );
```

لا توجد أي سياسة أخرى على هذا الجدول. طالب يستعلم عنه مباشرة بالمفتاح العام يحصل على **صفر صفوف** — لا خطأ يكشف وجود بيانات، ولا بيانات.

### ٢. التصحيح يحدث داخل قاعدة البيانات

دالة `public.submit_exam()` هي الجهة الوحيدة التي تقرأ `question_keys` أثناء الامتحان، وتعمل داخل Postgres. ما يعود منها **درجات فقط**. الإجابة الصحيحة لا تغادر قاعدة البيانات في هذه العملية إطلاقاً، فلا يوجد ما يمكن التقاطه من تبويب الشبكة.

### ٣. الإجابات تظهر في المراجعة بشرطين معاً

كل بيانات صفحة المراجعة تأتي من `public.get_attempt_review()`، وهي التي تقرر ماذا يُرسل:

- أن تكون المحاولة للطالب نفسه وقد سلّمها؛
- **و** أن يكون `reveal_answers` مفتوحاً لهذا الامتحان.

إن اختل الشرط، تصل الحقول السرّية بقيمة `null` **من قاعدة البيانات نفسها**. ليست ترسَل ثم تُخفى بـ CSS. حتى `is_correct` مخفي في هذه الحالة، لأن معرفة أن سؤال «صح أو خطأ» إجابته خاطئة هو نفسه كشف للمفتاح.

### ٤. المحتوى غير المصرَّح به لا يعود من قاعدة البيانات

الطالب لا يقرأ عنوان امتحان ولا اسم ملف لم يُمنح صلاحيته. الأمر ليس إخفاءً في الواجهة: سياسة `exams_select` تستدعي `can_access_exam(id)`، فترجع الاستعلامات صفر صفوف. وحتى نصوص الأسئلة لا تُقرأ إلا إذا كان الامتحان مفتوحاً أو كانت للطالب محاولة فيه، فلا يستطيع قراءة أسئلة امتحان جهّزته ولم تفتحه بعد.

### كيف تختبر هذا بنفسك

**الطريقة الأولى — سكربت جاهز يفعل ذلك نيابةً عنك.**

نفّذ `supabase/sql/07_security_check.sql` في SQL Editor. الملف ينتحل شخصية طالب حقيقي من قاعدة بياناتك، **بنفس صلاحيات متصفحه بالضبط**، ثم يحاول الوصول لما لا يُفترض أن يصل إليه: مفاتيح الإجابات، امتحانات محجوبة، بيانات طلاب آخرين، منح نفسه صلاحية، ترقية نفسه إلى مدرّس، فتح مراجعة زميله.

يعود بجدول فيه عمود **نجح**. المطلوب أن يكون `true` في كل صف. الملف داخل transaction ينتهي بـ `rollback`، فلا يغيّر بياناتك.

لكي يكون الاختبار ذا معنى، يجب أن يكون لديك طالب مفعّل واحد على الأقل، وامتحان واحد على الأقل **غير** مصرَّح له به.

**الطريقة الثانية — بيدك من متصفح الطالب.**

سجّل دخولاً بحساب طالب تجريبي، افتح **Console** في المتصفح، والصق:

```js
const url = "https://cpwhdvcfwngtlxzbgcmp.supabase.co";
const key = "sb_publishable_..."; // انسخه من مصدر الصفحة، فهو ظاهر فعلاً
const token = JSON.parse(
  Object.entries(localStorage).find(([k]) => k.includes("auth-token"))[1]
).access_token;

const ask = (path) =>
  fetch(`${url}/rest/v1/${path}`, {
    headers: { apikey: key, Authorization: `Bearer ${token}` },
  }).then((r) => r.json());

// مفاتيح الإجابات — المتوقع []
await ask("question_keys?select=*");

// كل الامتحانات — المتوقع أن يظهر ما فُتح له فقط
await ask("exams?select=id,title");

// بيانات الطلاب — المتوقع صفّه هو فقط
await ask("profiles?select=id,full_name,phone");

// محاولة منح النفس صلاحية — المتوقع رفض
await fetch(`${url}/rest/v1/permissions`, {
  method: "POST",
  headers: {
    apikey: key,
    Authorization: `Bearer ${token}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    student_id: "<ضع معرّفه>",
    resource_type: "exam",
    resource_id: "<معرّف امتحان محجوب>",
  }),
}).then((r) => r.status);
```

وجرّب أيضاً، وأنت في وسط امتحان، أن تفتح تبويب **Network** وتبحث في كل ما وصل عن أي إشارة إلى الإجابة الصحيحة. لن تجد شيئاً: ما وصل هو نص السؤال ونصوص الخيارات ومعرّفاتها فقط.

## ٨. جداول قاعدة البيانات وسياساتها

RLS **مفعّل على كل جدول بلا استثناء**، والافتراضي هو المنع: ما لا تسمح به سياسة صراحةً فهو ممنوع.

| الجدول | ماذا يقرأ الطالب | ماذا يكتب الطالب | ملاحظات |
|---|---|---|---|
| `profiles` | صفّه هو فقط | لا شيء | الاسم والهاتف يعدّلهما المدرّس وحده. الصف يُنشأ بـ trigger على `auth.users` بدور `student` وحالة `pending` دائماً |
| `chapters` | الفصل الذي فيه درس واحد على الأقل مرئي له | لا شيء | |
| `lessons` | الدرس الذي مُنحه، أو الذي فيه ملف أو امتحان مُنحه | لا شيء | الدرس عنوان يجمع محتوى، وما يبقى محجوباً هو محتواه |
| `lesson_files` | ما مُنحه فقط | لا شيء | `can_access_file` |
| `exams` | ما مُنحه فقط | لا شيء | حتى العنوان لا يظهر بدون صلاحية |
| `questions` | أسئلة امتحان مُنحه **و** مفتوح أو له فيه محاولة | لا شيء | لا يقرأ أسئلة امتحان مجهَّز ولم يُفتح |
| `question_options` | نفس شرط `questions` | لا شيء | **لا يوجد عمود `is_correct` في هذا الجدول** |
| `question_keys` | **لا شيء إطلاقاً** | لا شيء | سياسة واحدة للمدرّس فقط |
| `permissions` | صلاحياته هو | لا شيء | |
| `exam_attempts` | محاولاته هو | لا شيء | البدء بـ `start_exam()` والتسليم بـ `submit_exam()` |
| `answers` | إجاباته **أثناء الحل فقط** | إجاباته أثناء الحل | بعد التسليم تمر المراجعة عبر `get_attempt_review()`. و`WITH CHECK` يمنعه من كتابة درجة أو تصحيح لنفسه |
| `file_events` | أحداثه هو | لا شيء | يُكتب من السيرفر بالمفتاح السرّي |
| `heartbeat` | صف واحد | لا شيء | للـ cron |

المدرّس له صلاحية كاملة على كل ما سبق عبر سياسة `for all using (public.is_admin())`.

### التخزين

الـ bucketان (`files` للـ PDF و`answers` لصور الإجابات) **خاصّان بلا أي سياسة وصول**. RLS مفعّل على `storage.objects` وغياب السياسات يعني منع الجميع. كل وصول يمر عبر مسار على السيرفر يتحقق من الصلاحية أولاً ثم يصدر رابطاً موقّعاً ينتهي بعد ساعة:

- `GET /files/[fileId]` — يفتح ملف درس ويسجّل الحدث. `?download=1` للتحميل.
- `GET /answer-image?attempt=…&question=…` — يعرض صورة إجابة. المسار مشتق حسابياً من صاحب المحاولة، فتغيير باراميتر في الرابط لا يفتح صورة زميل.

الرفع أيضاً بروابط موقّعة تُصدر من السيرفر بعد التحقق، فيرفع المتصفح مباشرة إلى Supabase دون المرور بـ Vercel.

### الدوال

| الدالة | من ينادها | ماذا تفعل |
|---|---|---|
| `start_exam(exam_id)` | الطالب | يتحقق من الصلاحية وأن الامتحان مفتوح، ويعيد المحاولة القائمة إن وُجدت |
| `submit_exam(attempt_id)` | الطالب | يصحح آلياً ويحسب الوقت وتجاوز المدة |
| `get_attempt_review(attempt_id)` | الطالب والمدرّس | يبني صفحة المراجعة ويقرر ما يُكشف |
| `mark_feedback_seen(attempt_id)` | الطالب | يسجّل اطّلاعه على التصحيح |
| `grade_attempt(attempt_id, grades)` | المدرّس | يحفظ درجات المقالي ويعيد الحساب. قابلة للتكرار للتعديل |
| `void_attempt(attempt_id)` | المدرّس | يلغي محاولة ليعيد الطالب الحل |

جميعها `SECURITY DEFINER` وتتحقق من هوية المستدعي داخلياً، و`EXECUTE` عليها ممنوع على `anon`.

## ٩. حدود الباقة المجانية وما يجب أن تنتبه له

| المورد | الحد | الوضع |
|---|---|---|
| قاعدة بيانات Supabase | 500 ميجابايت | كافٍ جداً لأقل من 30 طالباً |
| تخزين Supabase | **1 جيجابايت** | ← اقرأ التحذير |
| توقّف المشروع | بعد 7 أيام سكون | يعالجه الـ cron |
| Vercel | 100 جيجابايت نقل شهرياً | كافٍ جداً |

### التحذير الوحيد المهم: مساحة التخزين

الحساب البسيط: 30 طالباً × 5 أسئلة مقالية × 20 امتحاناً × نصف ميجابايت للصورة = **1.5 جيجابايت**، أي أنك ستتخطى الجيجابايت الواحد قبل نهاية السنة، من غير أن نحسب ملفات الـ PDF أصلاً.

لذلك:

- صور الإجابات تُضغط **في متصفح الطالب قبل الرفع** إلى حوالي 300 كيلوبايت. والضغط يحافظ على الألوان ولا يحوّلها إلى أبيض وأسود، لأن التحويل الثنائي يبتلع خط الرصاص الخفيف.
- في صفحة كل امتحان زر **«امسح الصور»**. بعد أن تنهي تصحيح امتحان، اضغطه. الدرجات والملاحظات والنص المكتوب كله يبقى — الصور فقط هي التي تُمسح، وهي وحدها الثقيلة.

اعتد أن تمسح صور كل امتحان بعد تصحيحه، ولن تصل إلى الحد أبداً.

راقب الاستهلاك من **Supabase Dashboard → Settings → Usage**.

## ما لم يُبنَ عمداً

لا دفع ولا أسعار ولا اشتراكات — المنصة لا تتعامل مع المال إطلاقاً. ولا وضع داكن، ولا واجهة فيديوهات (قاعدة البيانات فيها حقل `video_url` مجهَّز وغير مستخدم)، ولا إشعارات بريد أو رسائل، ولا لوحات صدارة ولا أي مقارنة بين الطلاب: **كل طالب يرى بياناته هو فقط**.

## فحص قبل التنفيذ

```bash
npm run check
```

يشغّل الثلاثة معاً: فحص أنواع TypeScript، وESLint، وفاحص ملفات SQL في
`supabase/check-sql.mjs`.

الأخير يقارن ملفات الـ SQL ببعضها قبل أن تلصقها في Supabase: كل دالة
مُستدعاة معرّفة، وكل عمود مُشار إليه موجود، وكل قيمة enum ضمن نوعها، وكل
جدول عليه RLS وسياسة واحدة على الأقل، وكل نوع معدود مطابق لما في
`src/lib/types.ts`. لن يمسك كل شيء — التنفيذ وحده يفعل — لكنه يمسك أخطاء
الكتابة التي تكتشفها عادةً في منتصف اللصق.
